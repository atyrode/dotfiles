# One private Tern workspace

Open **`https://tern.tyrode.dev` in a browser** on each enrolled device. They attach to the same workspace on `dev-01`; closing a tab or shutting down a client does not stop a server-side shell. Connecting a native Tern window to `tern remote serve` over QUIC is a different path and is not how to join this browser view. There is no SSH port forward, tailnet account, public terminal endpoint or OIDC provider.

`tern-workspace-daemon` owns the panes, `tern-workspace-web` attaches to its Unix socket, and a private Caddy instance terminates HTTPS. Restarting the web frontend does not restart the daemon. A **server reboot** stops processes: Tern can restore its saved layout, directories and scrollback, not the memory of arbitrary running programs. The workspace starts empty once, not each time a device connects.

The workspace runs as `tern-workspace`, not the SSH administrator. Its writable home is `/var/lib/tern-workspace`, not `/home/alex`. Clone projects and authorize development tools in that account through their normal login flows; do not copy another account's sessions. Loss of this disk is not a reconnect: protect the workspace home with an appropriately private backup if recovery is required. [Stencil Tern](https://stencil.so/tern#everywhere) is a closed beta, not FOSS. WireGuard and Caddy are self-hosted; Tern 0.9.29's default web client fetches a versioned, integrity-checked WebAssembly asset from `build.stencil.so`. This setup is not a promise of offline operation or zero vendor contact.

## First provision

1. **Name and certificate.** Create a DNS-only A record `tern.tyrode.dev` → `10.219.83.1`. No proxy, public-address A, or AAAA. `dev-01.tyrode.dev` must still resolve publicly: it is the WireGuard endpoint, not the private website. Issue a dedicated Cloudflare API token with Zone:Read and DNS:Edit restricted to the DNS-01 validation zone. To avoid granting write access to the primary zone, delegate `_acme-challenge.tern.tyrode.dev` by CNAME into a separately managed zone and scope the token there. Where the server has a stable egress IP, restrict the token to it. In an authorized writable checkout, enter the token only at the hidden prompt:

   ```sh
   nix shell --inputs-from . nixpkgs#age-plugin-se -c \
     clan vars generate dev-01 --generator tern-workspace-dns --flake "$PWD"
   ```

   Publish the Clan-encrypted result through the usual review path, not the token. The private proxy will not serve the placeholder self-signed certificate. ACME renewals neither expose port 80 nor restart the Tern daemon. If a resolver filters private addresses in public DNS, add an exception for **this name** on the resolver you control or return that same A record in private DNS. Do not disable DNS-rebinding protection globally.

2. **Server.** Install the licensed Linux `tern` **0.9.29** from Stencil in the primary user's normal installer location (`~/.local/bin/tern`) if not already present. The system service checks the approved digest before publishing an executable into `/var/lib/tern-workspace-bin`; neither the executable nor Tern account state is redistributed in Git or Nix. An absent or different build fails closed. Review `atyrode apply dev-01 --preview-json` and apply the published revision through the normal [session-preserving activation](atyrode.md#the-mutation-boundary). Do not override a blocked disruption. The workspace's WireGuard and Mac peer keys are already enrolled through Clan, separate from fleet administration.

3. **Clients.** The [public peer inventory](../fleet/tern-workspace.nix) assigns one key and one address per device. A `null` peer key admits **no** device at that address. Never paste a private key or a WireGuard configuration into Git, chat or a debugging command.

   | Device | First setup | Afterwards |
   |---|---|---|
   | Mac (`macbook`) | Run `atyrode apply macbook`. nix-darwin configures WireGuard and its native launchd job from the machine's Clan key; no separate GUI profile or On-Demand switch. | The tunnel starts at boot. Use a browser on macOS. |
   | Windows (`wsl`) | Open **Windows Terminal as Administrator**, enter the managed WSL distro (`wsl -d atyrode-nixos`), and run `atyrode apply wsl`. Its Windows phase installs WireGuard and configures the native `atyrode-tern` tunnel, not a VPN inside WSL. Enroll the **public** key the phase reports as `peers.windows.publicKey`, publish and apply on `dev-01`. Running `atyrode windows plan` or `atyrode windows apply` in the managed distro inspects or reruns just that phase. WSL `sudo` alone does not elevate Windows. | Windows Service Control Manager starts the tunnel without WSL, a terminal, a tray window or another UAC approval. Leave unrelated profiles untouched; an automatically chosen local listen port is normal. |
   | iPhone | In the WireGuard app, create a tunnel and **generate a new key on the phone**. Enroll only its public key as `peers.iphone.publicKey`, publish and apply on `dev-01`. For the interface use `10.219.83.4/32`; for its one peer use the [server public key](../vars/per-machine/dev-01/tern-workspace-wireguard/publickey/value), endpoint `dev-01.tyrode.dev:51837`, Allowed IPs `10.219.83.1/32`, keepalive `25`. Leave DNS and listen port unset. Approve the iOS VPN permission and enable On-Demand for Wi-Fi and cellular. | iOS brings up the split tunnel. Open the same URL in a WebGPU-capable browser. There is no `atyrode apply` on iOS. |

4. **Pair each browser once.** WireGuard admits a device to the network; Tern separately authorizes a browser to control the workspace. Retrieve `/var/lib/tern-workspace/.config/tern/web-token` on `dev-01` **only in a private administrator terminal**, then use `https://tern.tyrode.dev/?token=…` for that browser's first successful connection. Treat that link like a shell password: no shared logs, tickets, screenshots or public bookmarks. Bookmark only the bare URL. Tern 0.9.29 remembers it in that browser's site storage; clearing site data, changing browser profiles or using private browsing can require pairing again. Do not configure the same token as a proxy credential or a DNS record.

## Verify and operate

- From a paired device, start a long-running command in a pane. Open the bare URL on a second paired device, confirm the **same pane and changing output**, and type into the same shell. Reboot a client; the URL should open without starting WireGuard manually. For the phone, try both cellular and Wi-Fi. This tests the workspace rather than just a status page or TLS certificate.
- On `dev-01`, `systemctl is-active wireguard-wg-tern tern-workspace-daemon tern-workspace-web tern-workspace-caddy` and `sudo wg show wg-tern latest-handshakes` separate application, ingress and peer failures. An enrolled client routes only `10.219.83.1/32`; the server accepts only that peer's address and HTTPS, not SSH or traffic between devices. Off-VPN clients should not reach the workspace even if they know its hostname and browser token. Private DNS resolution alone does not prove either a connection or an authorization.
- To revoke any device, set that peer's `publicKey` to `null` in the inventory, publish and apply on `dev-01`. For the Mac, replace the public-key reference rather than deleting Clan's generated files. No other device's key needs to change. If browser authorization may have leaked, also rotate Tern's browser token during an announced **frontend-only** maintenance window and pair the remaining browsers again. The daemon owns the panes.
- Browser authorization grants control of the shared development shell. This is not read-only guest access or a per-user permission model. Sharing just the hostname is harmless; do not hand out an existing peer's key or your browser link. Guests are outside this deployment.
